# 01 – Produkt, Zielgruppe und MVP

## 1. Problem statt Funktionen validieren

Eine App-Idee ist noch kein Produkt. Zuerst muss klar sein:

- Wer hat das Problem?
- Wann tritt es auf?
- Wie wird es heute gelöst?
- Was ist an der heutigen Lösung schlecht oder teuer?
- Warum würden Nutzer wechseln?
- Woran erkennt man, dass die neue Lösung funktioniert?

## 2. Produktformel

> Für **[konkrete Zielgruppe]** löst die App **[konkretes Problem]** durch **[Mechanismus]**, sodass **[messbares Ergebnis]** entsteht.

Schlecht: „Eine App für alle, die produktiver sein wollen.“  
Besser: „Eine App für Auszubildende im Schichtbetrieb, die Lernaufgaben schnell in kurze, planbare Einheiten zerlegen müssen.“

## 3. Nutzerinterviews

Frage nach tatsächlichem Verhalten, nicht nach hypothetischer Zustimmung.

Gute Fragen:

- Wann hattest du das Problem zuletzt?
- Was hast du konkret getan?
- Welche Lösung hast du schon ausprobiert?
- Warum hast du sie abgebrochen?
- Was kostet dich das Problem an Zeit, Geld oder Stress?
- Wer entscheidet über den Kauf?

## 4. MVP-Filter

Eine Funktion gehört in Version 1, wenn mindestens eines gilt:

1. Ohne sie kann der Kernablauf nicht beendet werden.
2. Sie verhindert ein relevantes Sicherheits- oder Rechtsrisiko.
3. Sie ist für Zahlung, Support, Export oder Löschung zwingend.
4. Sie erzeugt den Lernbeweis, den das Team für die nächste Entscheidung braucht.

Alles andere kommt in „später“ oder wird gestrichen.

## 5. Must-have-Artefakte

- Problemstatement
- Zielgruppenprofil
- Interviewnotizen
- Alternativen-/Wettbewerbsanalyse
- MVP-Liste
- Nicht-Ziele
- PRD
- Kernmetrik
- Beta-Erfolgskriterium
- Kill-Kriterien

## 6. Metriken

| Bereich | Beispiel |
|---|---|
| Aktivierung | Nutzer erreicht erstmals den Kernnutzen |
| Retention | Nutzer kehrt wegen des Kernnutzens zurück |
| Conversion | Nutzer schließt Kauf, Abo oder gewünschte Aktion ab |
| Qualität | Fehlerquote, Abbruchquote, Supportfälle |
| Wirtschaftlichkeit | variable Kosten, Deckungsbeitrag, Rückerstattungen |

## Gate 1 – Produktfreigabe

- [ ] Problem durch reale Beobachtungen belegt
- [ ] Zielgruppe eng genug definiert
- [ ] ein vollständiger Kernablauf beschrieben
- [ ] MVP und Nicht-Ziele getrennt
- [ ] Erfolgskriterium und Kill-Kriterien vorhanden
- [ ] wichtigste technische, rechtliche und wirtschaftliche Risiken dokumentiert
